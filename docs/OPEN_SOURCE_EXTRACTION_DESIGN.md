# Hotel PMS Community 抽离设计

## 1. 阶段与结论

- 阶段：架构抽离与独立仓库初始化。
- 源版本：`SaaS_JD origin/main@86c590f61ee2abe0deb20fed4b02668a721181e6`。
- 目标：形成可独立构建、可从空库运行、无生产配置的社区版酒店 PMS。
- 结论：以订房领域为公开核心；商业支付、分账及平台能力将在后续版本通过经过评审的公共契约接入，本次 MVP 不预建接口或事件框架。

## 2. 已确认事实

- 当前后端是 Java 8、Spring Boot 2.7.18、Maven 多模块项目。
- `yudao-module-booking` 已拥有房型、房间、库存、订单、订单锁和超时任务等主要领域对象。
- `yudao-module-booking` 直接依赖 `yudao-module-merchant`，后者依赖系统租户、用户、菜单和权限。
- 小程序聚合控制器同时访问 booking、dining、member、pay、settlement，不能直接进入社区版。
- 当前数据库脚本是基线 SQL 与多份增量 SQL 的组合，不能作为干净的社区版迁移直接发布。
- 当前仓库包含生产域名、AppID、服务器路径、部署脚本、真实品牌和验收材料。

## 3. MVP 范围

### 3.1 进入社区版

- 基础登录、用户、角色、菜单、租户隔离和操作日志。
- 酒店基础资料和酒店员工上下文。
- 房型、房间、房型设施、相册元数据。
- 每日库存、每日价格、库存调整记录。
- 多晚库存计算、订单幂等、库存锁定、支付超时释放逻辑（本地默认不启动调度器）。
- 订单确认、分房、入住、离店、未到店、取消。
- 管理后台对应页面。
- 通用文件存储、本地开发配置和数据库迁移。
- 手工支付状态流转，用于不接第三方支付的完整履约链路；不调用任何支付渠道。

### 3.2 不进入社区版

- 平台商户入驻、审核、商户列表、品牌内容运营和跨租户统计。
- 餐饮套餐、桌台、时段和餐饮订单。
- 酒店会员中心、已配置的微信登录、手机号授权和常用入住人账户体系。
- 微信普通商户、服务商支付、退款回调和支付证书配置。
- 平台抽佣、分账、分账回退、提现和财务汇总。
- OpenAPI 应用、令牌、业务范围和验收工具。
- 小程序及其 AppID、上传密钥、生产域名和商户图片。
- 生产部署、备份、证书、密钥归档和 CDN 运维脚本。

## 4. 目标架构

```text
hotel-pms-community
├─ yudao-server
│  └─ 仅装配 system、infra、merchant、booking
├─ yudao-module-booking
│  ├─ domain/service       房型、库存、订单、履约
│  └─ application         下单、取消、确认、入住、离店用例
├─ yudao-module-merchant
│  └─ property context    单酒店默认，多租户数据结构保留
├─ yudao-module-system
├─ yudao-module-infra
├─ yudao-ui/yudao-ui-admin-vue3
├─ db/bootstrap
└─ deploy
```

依赖方向必须满足：

```text
system/infra <- merchant <- booking <- server

future commercial adapters -> reviewed public contracts -> community services
community core -X-> commercial modules
```

## 5. 应用层边界

社区版先保持领域边界清晰，不为尚未接入的商业能力预建复杂框架。当前
MVP 的应用边界如下：

| 当前边界 | 职责 | 实现 |
| --- | --- | --- |
| 当前酒店上下文 | 当前酒店与租户上下文 | 商户上下文服务，所有订单操作使用当前酒店 |
| Booking application service | 下单、取消、确认、分房、入住、离店 | 社区核心直接实现 |
| 线下状态登记 | 登记已经在系统外完成的收款或退款 | 显式管理命令，不调用支付渠道 |
| 文件存储 | 图片和附件存储 | 沿用基础框架的本地数据库文件能力 |

后续若接入商业版，可评审 `PaymentGateway`、客户身份适配器和订单事实事件。
这些名称仅是候选设计，不是当前仓库已经承诺的 API；发布前必须补充版本、
幂等、失败恢复和兼容性测试。

HTTP Controller 只负责鉴权、参数校验和响应映射。库存锁定、价格计算、订单状态和退款决策必须位于 application/service 层。

## 6. 数据设计

- 首版保留 `tenant_id`、`merchant_id` 字段，默认初始化一个租户和一家酒店。
- 不进行删除租户框架的大规模重构，降低商业版同步成本。
- 从必需表生成 `db/bootstrap/00-framework-schema.sql`、`01-community-seed.sql` 和 `10-hotel-domain.sql`，禁止复制生产数据库导出。
- bootstrap 只用于空数据库首次初始化，不承诺对已有数据库重复执行。
- 演示数据使用虚构酒店、虚构手机号和本地图片。
- 所有金额继续使用整数分，日期库存使用酒店本地业务日期。
- 数据库基线必须覆盖唯一键、库存并发约束、订单幂等键及订单锁明细。

## 7. 管理端设计

社区版菜单只保留：

- 工作台
- 酒店资料
- 房型管理
- 房态与库存
- 酒店订单
- 入住管理
- 员工管理
- 系统管理中的用户、角色、菜单、文件和操作日志

移除平台运营、餐饮、财务、提现、支付应用、OpenAPI、商城、CRM、AI、工作流等入口。页面通过真实后端接口加载，空态、错误态和加载态不得回退到前端 mock 数据。

## 8. 配置与安全

- 所有外部地址通过环境变量或示例配置注入。
- 仓库只提交 `.env.example`、前端安全默认 `.env` 和环境变量驱动的 `application-local.yaml`。
- 禁止提交 AppID、APIv3 密钥、私钥、证书、服务器 IP、生产域名和真实数据库连接。
- 发布前扫描当前导出树和新仓库历史。
- 图片必须为项目自有、明确授权或生成的演示素材。

## 9. 开源治理

- 新业务代码使用仓库根目录的 MIT 许可。
- 上游 MIT 文件保留原版权和许可文本，不重写上游版权。
- 增加 `NOTICE`、`SECURITY.md`、`CONTRIBUTING.md`，并以 Maven POM 和 pnpm lockfile 记录依赖。
- 发布流水线可另行生成 CycloneDX SBOM；本次 MVP 不提交未经验证的静态 SBOM。
- 社区核心作为事实源；商业仓库通过 Maven 版本或受控同步依赖社区核心。
- 通用缺陷先修复社区核心，商业仓库只保留适配器和企业功能。

## 10. 实现分片

### Slice 1：干净导出

- 建立新仓库和来源说明。
- 按白名单复制后端基础、merchant、booking 和管理端。
- 排除商业模块与生产文件。
- 验收：敏感词扫描通过，源提交可追溯。

### Slice 2：后端独立装配

- 删除 server 对 dining、member、pay、settlement 的依赖。
- 删除跨模块聚合控制器。
- 建立安全的 local 启动配置和手工支付状态边界。
- 验收：Maven 编译和所选模块测试通过。

### Slice 3：数据库与演示环境

- 生成版本化基线迁移和虚构演示数据。
- 增加 MySQL、Redis、后端的 Compose 编排。
- 验收：全新数据卷一键启动并完成健康检查。

### Slice 4：管理端收敛

- 保留酒店页面和通用系统页面。
- 移除商业路由、API 和品牌配置。
- 验收：管理端类型检查与构建通过，真实接口空态和错误态正确。

### Slice 5：商业版反向接入（后续）

- 先设计并发布最小公共契约，再让商业支付、结算和平台模块依赖该契约。
- 对照现有业务链路进行回归。
- 验收：线上商业能力行为不变，公开核心不依赖商业模块。

## 11. 风险与停止条件

- 如果未来支付接入需要修改 booking，先完成契约设计与兼容性测试，不得把 pay 整包带入社区版。
- 如果系统/基础框架存在大量非酒店模块编译依赖，优先禁用模块装配，不进行无关源码重写。
- 如果发现任何有效凭据，立即停止发布，先轮换凭据，再继续清理。
- 如果清理管理端需要重写基础框架，首版允许保留未启用的通用基础页面，但禁止保留商业页面与生产配置。
