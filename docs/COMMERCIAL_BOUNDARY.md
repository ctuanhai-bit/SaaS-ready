# 社区版与商业版边界

## 社区核心

社区核心拥有酒店业务事实：房型、房间、库存、价格、订单、锁定、取消、入住和离店。库存是否可售、订单金额和状态只能由核心后端计算。

## 商业扩展

商业仓库拥有平台运营、餐饮、会员小程序、微信支付、退款、抽佣、分账、提现、OpenAPI 和生产运维。

当前 MVP 没有发布统一支付接口或领域事件总线。商业扩展接入前必须先评审并发布最小公共契约，之后只能：

- 实现已经发布且有兼容性测试的支付、身份或存储接口。
- 订阅已经发布的业务事件，不依赖社区模块内部实现。
- 增加独立管理页面和平台 API。
- 使用公开 API，不直接访问社区模块的 Mapper 或内部数据对象。

社区版现有的“登记线下收款完成”和“登记线下退款完成”只是订单状态命令，不是支付接口，不发起资金操作，也不能作为商业支付回调使用。

商业扩展不得：

- 修改社区库存或订单表来绕过领域服务。
- 让社区模块依赖商业模块。
- 在社区仓库保存生产配置或商业默认值。
- 将平台抽佣规则写入社区核心。

## 同步策略

- 社区仓库是通用酒店能力的事实源。
- 商业仓库固定依赖已发布的社区版本。
- 通用缺陷先提交社区仓库，再升级商业仓库依赖。
- 仅商业场景的改动留在商业适配器，不反向污染社区核心。
- 每次社区版本升级执行库存、订单、履约和租户隔离回归测试。
